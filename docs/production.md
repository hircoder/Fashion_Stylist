# Production notes: what it costs, how it scales, what to add

Everything below is measured on this code, on the popular-100K index, unless its marked as an
estimate. Raw numbers: `docs/bench_cpu.json`, `docs/bench_mps.json`,
`docs/live_run_sonnet.json`. The deck (`docs/overview.html`, slides 11 to 16) has the same
content in table form.

## Latency and throughput, measured

Retrieval only (`use_llm=false`), one process, M4 laptop pinned to CPU
(`python scripts/benchmark.py --device cpu --concurrency 1,2,4,8 --requests 60`):

| concurrency | p50 | p95 | req/s |
|---|---|---|---|
| 1 | 22 ms | 32 ms | 42 |
| 2 | 33 ms | 41 ms | 58 |
| 4 | 65 ms | 82 ms | 62 |
| 8 | 126 ms | 145 ms | 62 |

Throughput flattens at about 60 requests per second per process: the query embedding and
the matmul both hold the GIL, so threads dont help. More capacity means more processes (replicas), not more
threads. RSS after load is 1.0 GB (torch and the model about 0.5 GB, the float32 index
0.25 GB, the pandas catalog and bm25 the rest); the index loads in 0.1 s including a
sha256 of every file.

Full pipeline with the LLM, a 20 query live run (the set before the 8 brand queries were
added; kept as the cold-latency sample, indicative rather than versioned) with a cold
plan cache, `claude-sonnet-4-6` through an Azure endpoint:

| stage | p50 | p95 | share of total |
|---|---|---|---|
| plan (1 LLM call) | 5.2 s | 7.1 s | 45% |
| retrieve (all slots) | 0.13 s | 0.28 s | 1% |
| rerank (1 call per slot, in parallel) | 5.9 s | 6.9 s | 51% |
| total | 11.5 s | 13.5 s | |

2.9 slots and 3.9 LLM calls per request on average, 0 empty slots in 58, 12 warnings (most
of them "3 of 4 items chosen by the reranker"). Not bad for a cold cache. A burst of 8 concurrent requests finished
in 18.5 s with no errors (p50 8.7 s, slowest 18.5 s) under `LLM_CONCURRENCY=8`.

## Economics

Token counts come from the SDK usage fields, are returned in every response
(`llm_info.calls`, `input_tokens`, `output_tokens`) and are printed on the per-request
log line, so cost per request is a number you can read off, not an estimate.

| per request | mean | min | max |
|---|---|---|---|
| input tokens | 8,200 | 3,900 | 13,100 |
| output tokens | 760 | 250 | 1,380 |
| LLM cost at $3 / $15 per million (Sonnet class) | $0.036 | $0.016 | $0.060 |
| same traffic at $1 / $5 per million (Haiku class) | $0.012 | $0.005 | $0.020 |
| compute, 2 vCPU container at $20 a month, 40K requests a day | $0.00002 | | |

About 2,100 input and 195 output tokens per call. The two system prompts and the ten
candidate rows are most of the input, which is why prompt caching pays.

At 10,000 requests a day:

* ~$360/day, Sonnet class, as measured.
* ~$200/day with a 90% plan-cache hit rate + prompt caching (system prompts are marked
  cacheable in the adapter). The plan cache removes 1 of 3.9 calls.
* Under $100/day with a Haiku-class reranker on top.
* Capacity per replica, measured: 8-way burst in 18.5 s = ~0.43 req/s sustained at
  `LLM_CONCURRENCY=8`, ~35K LLM-mode requests/day (millions retrieval-only). Provider
  TPM quota binds before CPU.

Ways to cut the bill, in order of payoff: cache plans across replicas (Redis); rerank
with a smaller model (the paired eval says the reranker adds about a point of type-match,
its real value is constraints and reasons, so check those survive); cut candidate rows
to 8; one rerank call for all slots when there are at most 2.

## Getting the total under one second

97% of the 11.5 s is two LLM calls that run one after the other. Tuning them does not get
to one second, removing them from the synchronous path does. The ladder, each step with
what it buys:

1. Plan cache (in the code) and prompt caching (the anthropic adapter marks the system
   prompts cacheable). A repeated query costs 0 ms to plan; the total is then the
   rerank, 5.9 s. Not enough alone.
2. Semantic plan cache. Embed the query (5 ms, the model is already loaded), reuse the
   plan of the nearest cached query when cosine similarity is at least 0.92. Real traffic
   is Zipf shaped; 60 to 80% of requests would hit. Misses still pay the full plan.
3. Distilled planner. A small instruction model (Qwen2.5-1.5B or Llama-3.2-3B) finetuned
   on 10 to 20K (request -> plan json) pairs generated by the current planner with the same
   schema, served by vLLM on one L4 GPU: 150 to 300 ms for 250 output tokens, 1 to 2 s on
   CPU with a 4-bit build. Accept a 2 to 3 point drop on the labelled set for a 20x latency
   cut; keep the large model for data generation and for the asynchronous refinement below.
4. Cross-encoder reranker instead of the LLM. `bge-reranker-v2-m3` or
   `ms-marco-MiniLM-L6` scoring (query, title + attributes) pairs: 5 slots x 10 candidates
   is 50 pairs, 60 to 120 ms on CPU, 10 ms on a GPU. Constraints stay in the masks. Reasons
   come from the deterministic template that already exists, or are generated after the
   response has been sent and pushed over server-sent events to clients that wait.
5. Offline enrichment. Run the LLM once per catalog row at index time (product type,
   occasion, season, style tags, audience), one-time cost of $100 to $800 for 826K rows on
   a Haiku-class model. The type gate becomes exact and most of the reranker's job moves
   offline.
6. Retrieval from 130 ms to about 40 ms: pre-tokenised bm25 queries, int8 embeddings, an
   ANN index (HNSW) only once the catalog passes about a million rows.

Budget after the ladder:

* plan 10-300 ms + retrieve 40-130 ms + rerank 60-120 ms + select 1 ms.
* p50 ~250-600 ms, p95 under a second, ~$0.001/request with the GPU amortised.
* Lost: the big model's judgement on odd requests + written reasons. Keep it as a
  background refinement ("better picks in 8 s") and the training-data source.
* Independent win: per-slot SSE streaming puts retrieval-order products on screen in a
  couple hundred ms; reranked order swaps in as calls land.

## Recommended production setup

| piece | recommendation | why |
|---|---|---|
| runtime | the existing container (python:3.12-slim, CPU torch), 2 vCPU / 4 GB per replica, 8 GB for the full 826K index | 1.0 GB RSS measured for 100K rows, 3.3 GB for 826K; query embedding is 5 to 10 ms on CPU, a GPU buys nothing at this size |
| processes | 1 uvicorn worker per replica, 3 replicas across zones, autoscale on in-flight requests (target 6 per replica) | stateless; one worker keeps LLM_CONCURRENCY and the rate limiter meaningful per replica |
| index artifact | tarball in object storage, pinned by INDEX_URL + INDEX_SHA256, rebuilt by a scheduled job when the catalog changes | verified download, safe extraction, atomic install and fail-closed loading exist already |
| platform | Railway or Fly.io for a team of one; ECS Fargate, Cloud Run or Kubernetes inside a platform that already runs one | no database, no queue, no GPU |
| LLM | Claude Sonnet class for plan and rerank, Haiku class as the cost option, prompt caching on, a second provider as failover | the adapters hide the SDK; the provider switches by environment |
| shared state | Redis for the plan cache (normalised query + model + prompt version, 24 h TTL) and for the rate limiter | both are per process today; three replicas triple the limits and cut the hit rate |
| edge | TLS, CDN for `/assets`, WAF rate rules, request size limit at the edge too | the in-app limits are the second line |
| secrets | platform secret store or Vault, rotated keys, nothing in images or logs | the settings repr hides keys, errors are scrubbed, queries are not logged unless LOG_QUERIES=1 |

Sizing:

* Retrieval-only: ~60 req/s per vCPU pair.
* LLM traffic: ~0.43 req/s per replica (measured burst at LLM_CONCURRENCY=8, not a
  formula; the calls overlap too much for one).
* Memory: index bytes x 2 (float16 disk, float32 RAM) + ~600 MB fixed.
* Startup 10-20 s incl. index download. Readiness `/ready` (60 s initial delay),
  liveness `/health`.

Settings that matter: `REQUEST_DEADLINE_S=40 PLANNER_BUDGET_S=15 RERANK_BUDGET_S=20
LLM_CONCURRENCY=8 MAX_INFLIGHT_REQUESTS=16 RATE_LIMIT_PER_MINUTE=60 MAX_BODY_BYTES=16384
CORS_ALLOW_ORIGINS=https://app.example STARTUP_FAIL_FAST=1 LOG_QUERIES=0 INDEX_URL=...
INDEX_SHA256=...`.

## Guardrails in place

* Input: strict schema (unknown fields rejected, query 1 to 500 chars, k 1 to 10, finite
  prices, min <= max), 16 KB body cap, 60 requests a minute per client, 16 in-flight
  requests per process.
* LLM: structured output only, every id validated against the offered candidates, picks
  capped at k, reasons capped at 15 words with urls and emails stripped, catalog text
  labelled untrusted in the prompt, the request passed as json data, no tool use.
* Budgets: one 40 s deadline, 15 s plan, 20 s rerank, 8 LLM calls in flight per proces,
  retrieval pool bounded with deadline-aware queueing, typed LLM errors.
* Data: checksum-verified index, fail-closed loader, safe tarball extraction (scheme
  allowlist, public hosts only, member caps, fixed permissions), keys never in repr,
  errors or logs. Residual: the host check is a resolve-then-connect pair, so DNS
  rebinding between the two is not caught; INDEX_URL is operator configuration.

Fallback ladder (degradations land in `warnings`; no-key mode shows in `llm_info`; a
missing index or tripped limit is an http error):

* Planner error/timeout -> regex planner (30 s negative cache against stampedes).
* One rerank call fails/late -> that slot keeps retrieval order.
* Reranker rejects everything -> type matches in retrieval order, or an empty slot.
* Slot below k in the price window -> flagged unpriced backfill (inferred bound only).
* Index missing at boot -> `/health` explains, `/ready` + `/recommend` 503 (or exit
  with `STARTUP_FAIL_FAST`).
* No key -> `LLM_PROVIDER=none`, plain search.

| errors | exception tracking with request id and scrubbed context | Sentry |

## Gaps and the plan

| gap | why it matters | plan |
|---|---|---|
| relevance is judged by 28 hand written rules | type-match says nothing about fit, style or purchase intent | weeks 1 to 2: 200 labelled queries (3 graders), nDCG@4 and slot recall, LLM-as-judge calibrated on the labels, nightly in CI |
| no online signal | offline metrics drift from behaviour | week 3: impression and click logging keyed by request_id, a holdout, CTR per configuration, A/B on prompt version and reranker model |
| latency is LLM-bound | 11 s median is fine for a stylist page, too slow for search-as-you-type | week 2: prompt caching, Redis plan cache, Haiku-class rerank behind a flag, SSE partial results; then the ladder above |
| no outfit coherence | slots are ranked independently | weeks 4 to 5: a coherence pass over the top 3 per slot (colour and style fields), evaluated on the labelled set |
| catalog scale | brute-force matmul is fine to about a million rows | HNSW with the masks applied after search, int8 embeddings, catalog served from parquet row groups |
| single language, single tenant | prompts and the audience heuristic are English only | multilingual embedding model (bge-m3), a language field in the plan, per-tenant index and prompt version |
| no personalisation | size, past purchases, brand affinity ignored | a profile object merged into the plan the way request fields are: explicit beats inferred |
