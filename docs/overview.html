Fashion stylist: what i built, why, and how it holds up

The brief: a small service that takes a sentence like the one below, works out what the person actually needs, and finds it in the Amazon Fashion catalog (826,108 listings) using semantic search and an LLM. Exposed as an API. This page is the short version; the README and docs/ have the long one.

Scope and why it matters

A catalog search box understands product words. People don't always have one. "I need an outfit to go to the beach this summer" has no product word in it, and the budget, the audience or the occasion hiding in a sentence get dropped on the floor by keyword search.

What i built: an LLM reads the sentence and writes a retrieval plan, one to five product types (i call them slots), each with a listing-style query, a few title keywords, words to avoid, and a share of the budget. Hybrid search finds candidates per slot inside the constraints. The LLM then picks the final items and says why. It's a FastAPI endpoint (POST /recommend), a CLI, and a small React page on top.

Why a business would care, in one breath: one search box that accepts situations instead of product names, bundles instead of single items, and a response that explains itself (which planner ran, what was filtered, why each pick) so it can be trusted in a real product rather than demoed once.

What the data allowed

I profiled every row before writing code, and it changed the plan. Two of the fourteen fields in the brief are empty on every single row (categories, bought_together), so there's no taxonomy and no "people also bought". Price exists for 6% of listings. The title is the one field that is always there and it's dense: brand, gender, type, colour, size, all in a median of 89 characters.

Popular listings are much better documented (right table), which is why the default index is the 100K most rated rows: 3 minutes to build and the LLM has something to explain. It's a bias, so it is stated in every response and measured against a random sample and the full catalog in the evaluation.

Other things i found: 56,720 titles repeat under different ids (size and colour variants). bm25 alone is hopeless on sentences ("outfit for the beach" matched toddler outfits and a cat purse) but perfect on brand names, 32/32 against 25/32 for embeddings alone. Of three small embedding models, bge-small-en-v1.5 gave the most sensible results at 761 docs/s on the laptop gpu; MiniLM was faster and clearly worse.

How a request runs

Offline, ingest streams the raw json into a typed parquet file (30 s for all rows) and build-index embeds a subset with bge-small and builds bm25 over the same text. The index folder is self contained: embeddings, bm25, the rows it covers, checksums. It can be tarred and shipped.

The decisions i'd defend

  • Constraints are masks on the full score vectors, applied before top-N. Filtering after retrieving 60 candidates quietly gives you empty slots when the eligible items sit at rank 61. With masks, one women's sandal under $30 anywhere in the index is enough. It costs microseconds.
  • Two channels fused with reciprocal rank fusion: dense for conversational phrasing, bm25 for brands and exact phrases. No score calibration needed.
  • One rerank call per slot, run in parallel. Five slots in one call took 20 s because output tokens dominate; five parallel calls take what one takes, and a failing slot keeps retrieval order instead of sinking the request.
  • Prices two ways. An explicit max_price is a hard filter. A budget read out of the sentence keeps unpriced items in the ranking, flagged price_known: false. Before that rule the blazer slot came back with a priced wooden ring, because 94% of items have no price.
  • Variants grouped at query time. "(8 B(M) US, Silver)" style suffixes make one product look like five; a title-derived key collapses them and it's computed at query time so a fix never needs a 20 minute rebuild.
  • Every provider failure (timeout, rate limit, refusal, bad json, anything) is a typed error with a fallback, and the response says which fallback ran.

What it can do

  • Outfit decomposition. "what to wear to an outdoor wedding" becomes shirt, pants, blazer, shoes, tie. A single item request stays one slot.
  • Constraints from the sentence: audience ("my husband", "my 6 year old daughter"), occasion, season, a per item or total budget. A total is split across slots by the planner, with a 10% floor per slot and scaling so the parts never exceed the total.
  • A one sentence reason per pick, the evidence fields it used, the title keywords it matched.
  • price_known on every item. Strict when you give a bound, flagged when i inferred one, never a claim it can't back.
  • Look-alike control: planner exclude words push cover-ups out of the swimsuit slot, and the reranker is told which candidates look off-type.
  • Degrades instead of failing. No key, a timeout, a rate limit, a refusal: the regex planner and retrieval order take over and warnings says so.
  • Same request model on three surfaces: the endpoint, stylist recommend "..." on the command line, the page.
  • Per stage timings, which planner and which index answered, a request id in the logs, a 504 when retrieval itself blows the deadline.
  • Index checksums and row alignment verified at startup; a prebuilt index can be installed from a url with sha256, size cap and safe extraction.

"what should my husband wear to an outdoor wedding in june, budget 200 total". Five slots, audience men, the planner split the total into shirt $38, pants $45, blazer $52, shoes $45, tie $20.

The first version filtered every slot to priced items and the blazer slot came back with a $13 wooden ring and a pair of linen shorts. Only about 11K of the 100K items carry a price and almost no blazer is among them. That's the run that changed the price policy: budgets read from the sentence now keep unpriced items in the ranking (flagged), the reranker is told type comes before price, and planner exclude words push look-alikes away. The same query now gives an Eddie Bauer travel blazer and oxford dress shoes, both marked price_known: false, next to priced shirts, pants and a silk tie set inside their shares.

Honest caveat: planner output varies between runs (slot names and counts change), so eval differences under about 2 points are noise.

How i tested it

244 tests. make test runs the fast ones in about 10 seconds with a hashed embedder and a scripted fake LLM, make test-all adds the real model and a live LLM round trip. What they're for:

  • Parsing and normalising: prices with thousands separators and ranges, the audience guess, variant keys, plan cleanup (slot caps, keyword dedupe, budget splits that never exceed the total).
  • Ranking: masks, fusion with a channel switched off, keyword boosts and penalties, grouping, the unpriced pool, a window that's full of variants of one product.
  • Failure paths: every LLM error class, a slot that fails while the others succeed, a stuck planner, retrieval past the deadline (504) while the concurrency permit stays held until the thread ends, five overlapping slots, 20 concurrent requests.
  • Artifacts: tampered embeddings, swapped row ids, an edited bm25 file, a missing bm25 directory, a lone meta.json, bad checksums, path traversal and symlinks in a tarball, a size cap counted on bytes actually written.
  • Contracts: both provider adapters against a recording fake of the SDK client, unknown request fields rejected, non finite numbers rejected, one error body shape.

CI runs the suite, lint, then builds the image without the baked index, indexes the fixture inside the container and hits /ready and /recommend.

Documented

The README covers setup, sample usage and the design decisions. docs/design-notes.md is the longer why, docs/evaluation.md the numbers and their caveats, the notebook the data profile and the model comparison, docs/architecture.pdf the diagram. /docs on the running service is the OpenAPI contract with examples.

Served

make demo builds a tiny index from the committed fixture in a minute, no download and no key. make data, make ingest, make index for the real catalog, make serve for the API with the page at / and this deck at /overview. The Docker image bakes a 40K item index at build time and runs on Railway with /ready as the health check; an LLM key as a service variable switches on the planner and reranker.
